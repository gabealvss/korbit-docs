Os tipos de evento são versionados (`*.v1`) — mudanças incompatíveis geram uma nova versão, nunca quebram seu consumidor. Você escolhe explicitamente os tipos que quer receber ao criar a assinatura.

## Pagamentos

| Evento | Quando dispara |
| --- | --- |
| `payment.created.v1` | Payment intent criado |
| `payment.requires_action.v1` | Ação do comprador pendente (PIX gerado ou 3DS) |
| `payment.succeeded.v1` | Pagamento confirmado pelo provedor |
| `payment.failed.v1` | Recusado ou expirado |

## Refunds

| Evento | Quando dispara |
| --- | --- |
| `refund.requested.v1` | Refund solicitado (inclui prazo de resposta quando aplicável) |
| `refund.updated.v1` | Estado do refund/caso mudou |
| `refund.succeeded.v1` | Refund liquidado |

## Saques

| Evento | Quando dispara |
| --- | --- |
| `payout.requested.v1` | Payout solicitado (valor reservado) |
| `payout.updated.v1` | Aprovação, execução, reconciliação ou falha |

## Disputas

| Evento | Quando dispara |
| --- | --- |
| `dispute.opened.v1` | Chargeback/med aberto pelo comprador |
| `dispute.updated.v1` | Evidência, decisão ou estado mudou |

## Conta

| Evento | Quando dispara |
| --- | --- |
| `merchant.kyc.updated.v1` | Progresso da verificação KYC/KYB |
| `merchant.status.updated.v1` | Status/capacidades da conta mudaram |

## Assinaturas recorrentes

Eventos do ciclo de vida das [assinaturas](/pagamentos/assinaturas) que seus clientes contratam. Cada fato do ciclo de vida gera um evento, publicado no ambiente (`test` ou `live`) da própria assinatura.

| Evento | Quando dispara | `status` no payload |
| --- | --- | --- |
| `subscription.created.v1` | O checkout criou a assinatura, que aguarda o primeiro pagamento | `PENDING_AUTHORIZATION` |
| `subscription.activated.v1` | O primeiro pagamento foi aprovado | `ACTIVE` |
| `subscription.renewed.v1` | Uma renovação foi paga, inclusive quando uma retentativa recupera uma assinatura em atraso | `ACTIVE` |
| `subscription.payment_failed.v1` | A primeira cobrança ou uma renovação foi recusada | `PENDING_AUTHORIZATION` ou `PAST_DUE` |
| `subscription.canceled.v1` | As renovações foram interrompidas. O comprador mantém acesso até `access_until` | `CANCELED` |
| `subscription.expired.v1` | O acesso terminou | `EXPIRED` |
| `subscription.plan_change_scheduled.v1` | Uma troca de plano foi agendada para o próximo ciclo | status atual (em geral `ACTIVE`) |

<Tip>
Para liberar ou bloquear acesso ao seu produto, use `access_until`, não só o `status`: uma assinatura `PAST_DUE` (em carência) ou `CANCELED` continua com acesso até essa data. O acesso termina de fato quando chega `subscription.expired.v1`.
</Tip>

### Campos do payload

O objeto `data` é um snapshot da assinatura no momento do evento. Campos sem valor são **omitidos** (não chegam como `null`).

| Campo | Tipo | Descrição |
| --- | --- | --- |
| `id` | UUID | ID da assinatura, o mesmo de `GET /v1/subscriptions/{id}` |
| `status` | string | `PENDING_AUTHORIZATION`, `ACTIVE`, `PAST_DUE`, `CANCELED` ou `EXPIRED` |
| `version` | inteiro | Versão da assinatura. Cresce a cada mudança; use para ordenar eventos (veja abaixo) |
| `order_id`, `customer_id` | UUID | Pedido de origem e cliente |
| `product_id`, `offer_id`, `price_id` | UUID | Produto, oferta e preço contratados |
| `amount_minor` | inteiro | Valor do plano em centavos |
| `currency` | string | Sempre `BRL` |
| `payment_method` | string | `CARD` ou `PIX` (Pix Automático) |
| `billing_interval`, `interval_count` | string, inteiro | Cadência: `MONTH` com 1 (mensal) ou 3 (trimestral), ou `YEAR` com 1 (anual) |
| `current_period_start`, `current_period_end` | data ISO 8601 | Ciclo vigente |
| `access_until` | data ISO 8601 | Até quando o comprador tem acesso |
| `next_billing_at` | data ISO 8601 | Próxima cobrança agendada, se houver |
| `cancel_at_period_end` | booleano | A assinatura termina ao fim do ciclo atual |
| `renewal_stopped_at` | data ISO 8601 | Quando as renovações foram interrompidas |
| `scheduled_price_id` | UUID | Preço que entra no próximo ciclo (`plan_change_scheduled`) |
| `invoice_id`, `payment_intent_id` | UUID | Fatura e cobrança que originaram o evento (pagamentos e falhas) |
| `cancellation_reason` | string | Só em `subscription.canceled.v1`. Veja os valores abaixo |
| `expiration_reason` | string | Só em `subscription.expired.v1`. Veja os valores abaixo |

**`cancellation_reason`**

| Valor | Significado |
| --- | --- |
| `MERCHANT_REQUEST` | Você cancelou, pelo painel ou por `POST /v1/subscriptions/{id}/cancel` |
| `CUSTOMER_REQUEST` | O comprador cancelou no portal do cliente |
| `INITIAL_PAYMENT_FAILED` | A primeira cobrança não foi concluída |
| `ACCOUNT_RESTRICTED` | A conta foi bloqueada e suas assinaturas foram encerradas |
| `PROVIDER_CANCELED` | A autorização recorrente foi cancelada fora da Korbit: pelo comprador no app do banco (Pix Automático) ou pelo próprio meio de pagamento |

**`expiration_reason`**

| Valor | Significado |
| --- | --- |
| `CANCELED_ACCESS_ENDED` | Uma assinatura cancelada chegou ao fim do período pago |
| `GRACE_PERIOD_ENDED` | A carência de uma assinatura em atraso (`PAST_DUE`) acabou sem pagamento |

### Ordem e duplicidade

Webhooks podem chegar fora de ordem ou repetidos. Guarde o maior `version` processado por assinatura e ignore eventos com `version` menor ou igual. Para deduplicar a entrega em si, use o `id` do envelope.

  "environment": "live",

### Testar no sandbox

Com uma assinatura de teste, use `POST /v1/test/subscriptions/{id}/simulate` (veja [Sandbox](/api-reference/sandbox)) para avançar o ciclo sem esperar o calendário: `PAY_INVOICE` gera `subscription.activated.v1` (primeira fatura) ou `subscription.renewed.v1`, e `FAIL_INVOICE` gera `subscription.payment_failed.v1`. Cancelar pela API gera `subscription.canceled.v1`.

## Formato do payload

Toda entrega tem o mesmo envelope. O conteúdo de `data` varia por tipo de evento.

```json payment.succeeded.v1
{
  "id": "2c7e9a14-6b3d-4f8a-9e21-7d5c4b3a2f10",
  "type": "payment.succeeded.v1",
  "occurred_at": "2026-10-01T12:00:00.000Z",
  "environment": "live",
  "data": {
    "id": "8f4b2c1d-3e5a-4b6c-9d7e-0f1a2b3c4d5e",
    "amount_minor": 14990,
    "currency": "BRL",
    "payment_intent_id": "8f4b2c1d-3e5a-4b6c-9d7e-0f1a2b3c4d5e",
    "payment_method": "PIX",
    "status": "SUCCEEDED"
  }
}
```

| Campo | Descrição |
| --- | --- |
| `id` | ID único do evento. Use como chave de deduplicação: o mesmo evento pode ser entregue mais de uma vez |
| `type` | Tipo versionado do evento |
| `occurred_at` | Quando o fato aconteceu na Korbit (ISO 8601, UTC) |
| `environment` | `test` (sandbox) ou `live` (produção) |
| `data` | Snapshot do recurso no momento do evento |

- Campos são `snake_case`; `amount_minor` em centavos (BRL).
- O snapshot traz os campos relevantes de cada tipo (ex.: `refund_initiator` e `review_deadline_at` em eventos de refund). Campos sem valor são omitidos.
- Dados pessoais do comprador (documento, e-mail, telefone, endereço) e dados de cartão nunca vão no payload. Consulte a API quando precisar deles.
- O objeto acima é o corpo da requisição. Os cabeçalhos de assinatura seguem o padrão Svix; veja [Verificação de assinatura](/webhooks/assinatura).

<Note>
Este catálogo é a fonte oficial dos tipos versionados. Novos eventos podem ser adicionados mantendo a versão; assine só o que sua integração consome.
</Note>
